# 8. Dalla context map a NestJS + CQRS

*I pattern ddd-crew diventano confini di import*

← [Separarsi o demarcare](7.separarsi-o-demarcare.md) · [Indice](README.md)

---

Riferimento: [ddd-crew/context-mapping](https://github.com/ddd-crew/context-mapping).

Contesto: monolite NestJS modulare, un modulo NestJS per ciascun bounded context (`ContextAModule`, `ContextBModule`, …), CQRS (`@nestjs/cqrs`) con `CommandBus` / `QueryBus` / `EventBus`. Il [percorso 10](../10.Moduli/README.md) parla di moduli in generale; qui i pattern di questa sezione prendono forma concreta.

## Relazioni tra team (macro-livello)

| Pattern | Descrizione (DDD) | Cosa significa nel monorepo/monolite |
|---|---|---|
| **Mutually dependent** | I due contesti devono evolvere e rilasciare insieme, forte accoppiamento reciproco. | Da evitare in generale: se non riesci a modificare un modulo senza toccare l'altro quasi a ogni commit, il confine è mal tracciato. |
| **Upstream / Downstream** | Le azioni dell'upstream influenzano il downstream, non viceversa. | Un modulo è upstream su un concetto (es. gestisce l'aggregate «principale»), l'altro è downstream e lo consuma. Si applica **per concetto**, non necessariamente per l'intero modulo. |
| **Free** | Nessun legame tra i due. | Nessuna dipendenza NestJS tra i due moduli, nemmeno indiretta. |

## Pattern → implementazione NestJS CQRS

| Pattern | Descrizione (DDD) | Come si implementa in NestJS CQRS |
|---|---|---|
| **Open Host Service (OHS)** | L'upstream espone un protocollo/set di servizi pubblico. | Un sotto-modulo `ContextPublicApiModule` (o cartella `context/public-api/`) che esporta **solo** un set ristretto di Commands/Queries + DTO. Gli altri moduli importano solo questo, mai handler interni o entity ORM. |
| **Published Language** | Linguaggio comune, documentato, per scambiare informazioni (spesso con OHS). | Package/cartella condivisa (es. `libs/contracts` in Nx, o `shared-kernel/dto` nel monolite) con **solo** interfacce/DTO/classi evento, versionate. Zero logica di dominio. |
| **Anticorruption Layer (ACL)** | Il downstream traduce per non corrompere il proprio modello. | Una classe `AntiCorruptionLayer`/`Adapter` nel consumer: riceve il DTO esterno e lo mappa nel modello interno. L'handler CQRS non usa il DTO esterno oltre questo punto. |
| **Conformist** | Il downstream adotta il modello upstream senza tradurlo. | Il consumer usa direttamente il DTO dell'OHS come modello di lettura, senza ACL. Più veloce; ogni cambio di contratto upstream si propaga senza filtro. |
| **Customer/Supplier** | Le esigenze del downstream entrano nel backlog dell'upstream. | Non è codice, è processo: la Query/DTO del `PublicApiModule` è un contratto versionato; le modifiche passano da issue/PR concordate, non da accesso alle entity interne. |
| **Partnership** | I team coordinano sviluppo e rilasci in modo stretto. | A livello di codice poco cambia rispetto a OHS/ACL: PR incrociate, review reciproche, stesso ciclo di rilascio. Nel monolite entrambi i moduli si deployano insieme — il «costo» della partnership è già basso. |
| **Shared Kernel** | Un sottoinsieme di modello (codice, DB) condiviso esplicitamente. | Cartella `shared-kernel/` con **solo** value object primitivi senza comportamento business (id tipizzati, enum davvero identici). Ogni modifica richiede coordinamento. Tenerlo piccolo. |
| **Separate Ways** | Nessuna relazione significativa. | Nessuna dipendenza NestJS: nessun import, nessuna query/comando condiviso. |
| **Big Ball of Mud** | Modello confuso — pattern negativo, da isolare. | Segnale: un modulo che importa repository/entity interne di un altro. Disciplina sui barrel export (`index.ts`): solo Commands/Queries/DTO pubblici. |

## Confini di import

```text
src/
  context-a/
    domain/                 # non esportato fuori dal modulo
    application/
      commands/
      queries/
      handlers/
    infrastructure/          # repository, ORM entity — non esportati
    public-api/              # ciò che gli altri moduli possono importare
      queries/...
      dto/...
      context-a-public-api.module.ts
    context-a.module.ts
  context-b/
    domain/
    application/
      commands/
      queries/
      handlers/
      acl/                    # traduce i DTO esterni nel modello di context-b
    infrastructure/
    context-b.module.ts      # importa SOLO ContextAPublicApiModule
  shared-kernel/              # VO minimi condivisi (opzionale, piccolo)
```

Regola in code review: se un file in `context-b/` importa qualcosa da `context-a/` che **non** passa da `context-a/public-api/`, è una violazione del confine (rischio Big Ball of Mud).

## Note

- Nel monolite, OHS + Published Language sono soprattutto **disciplina sui barrel export**, non HTTP/gRPC: la «rete» è `QueryBus` / `CommandBus` in-process.
- Se un modulo diventa un servizio separato, `public-api/` è il punto naturale da trasformare in endpoint o eventi su broker, senza toccare il resto del dominio.
